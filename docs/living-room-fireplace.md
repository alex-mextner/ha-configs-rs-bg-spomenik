# Fireplace and YouTube on the living-room projector

The existing `script.living_room_fireplace` remains the voice entry point: «включи камин на проекторе». It uses the existing paired projector/Kodi power action and native `media_player.home` entity. Commands are queued, with a maximum of three pending/running executions.

## Existing power integration prerequisite

This package extends the installed living-room power integration. Before any power action, it requires `media_player.projector.power_intent_revision`, `binary_sensor.projector_hdmi_connected`, and `sensor.kodi_service_state`. The fireplace calls `script.projector_start_for_playback` to explicitly start the paired projector and Kodi or wait for an existing startup. The projector also exposes `last_power_intent`, `power_sync_target`, and `power_sync_error`. The older TV-only configuration in a fresh checkout does not supply this contract. The fireplace script aborts before calling that legacy route when the capability is absent, and its HA regression covers this boundary. Deployment must verify the producing integration in the active installation and preserve it.

Before those capability checks, the script refreshes the projector entity and requires a newer `last_reported` publication. Home Assistant can swallow a device refresh error while retaining cached attributes; that unchanged publication must not authorize power. A successful identical publication is accepted even when `last_updated` is unchanged.

The manifest and HA endpoints target the existing bridge at `172.20.0.1:8787`. A different bridge bind requires updating the HA URLs, resolver and adapter together; this feature does not silently retarget another host.

## Source selection and evidence

The controller selects from `scripts/host/kodi_fireplaces.json`. It excludes the last successfully played source and any currently owned source, shuffles eligible YouTube videos, tries at most two, and then tries only explicitly eligible licensed local alternatives. An entry with `selectable: false` is retained for attribution or old ownership recognition and is never selected. At this candidate checkpoint all local entries are disabled; failure of both YouTube attempts reports an unconfirmed/failed launch instead of opening a rejected clip. Resolver failures never update selection history. Successful history is written atomically only after Kodi reports the expected media, repeat-one, and an advancing playback position. Restarting the bridge or stopping playback preserves that history.

A source is an independent video, not another resolution of the same upload. The selectable YouTube catalog uses wide views with the fireplace or stove surround and adjacent wall visible. Music comes from the separate Evening Station action.

The former close-up sources (`2rkB6CNfqJ4`, `W1NI3lfdMug`, and `kBlOvm_kiCk`) remain in the catalog with `selectable: false`. Their IDs must remain recognizable for durable playback ownership and recovery until a new confirmed source replaces them. They are not eligible for selection or fallback.

AISIS supplies a `request_id`; direct HA/UI and Yandex script calls generate one. The controller publishes `starting` before extraction and keeps status reads responsive. A `playing` receipt includes that request ID, `launch_started_at`, fresh `observed_at`, `source_id`, `source_kind`, actual native title, `owned`, `file_matches`, `repeat`, and `progressing`. HA and AISIS cross-check the title against native Kodi state. Polling an old video cannot confirm a new request.

A transport timeout after the single `Player.Open` is reconciled through read-only native state within a separate 45-second startup-confirmation allowance, capped by the remaining shared launch deadline. During native startup, transient read failures restart the complete active-player/item/properties snapshot under that same deadline, including lease validation and repeat confirmation, without replaying mutation commands. Open, Stop and SetRepeat mutation transport calls remain capped at eight seconds, and reads at one second. A definite HTTP or JSON-RPC rejection fails immediately; an outcome still unconfirmed after reconciliation produces `unknown` and never triggers a duplicate Open. Cancellation is checked before each launch-time RPC. Definitive source failure produces `error` with a fixed code. An identified but stalled owned source is stopped and confirmed released before another candidate opens. That automatic replacement rechecks native emptiness and repeat intent immediately before Open. Missing playback during an unresolved launch retains its cleanup identity; an empty or malformed response alone is not proof that the exact source was stopped. Preparation has a 45-second subprocess allowance per source; the complete host launch shares a 100-second deadline, plus bounded cleanup. Both source resolution and playback verification consume that shared budget. The HA request timeout is 120 seconds, leaving room for existing cleanup and process reaping. Warm requests still finish as soon as playback progresses. The cold projector/Kodi readiness wait allows at most 120 seconds and exits immediately on readiness or a newer power intent; voice may report pending before physical power and playback finish.

Preparation timeouts are reported as `source_resolution_timeout` when no source reached playback; unavailable sources and post-Open failures retain their existing semantics. The bridge records request, attempt and source IDs with preparation start/ready/failure, elapsed time and remaining allowance. The resolver records HTTP start/response/failure with elapsed time and fixed exception type/status. Native RPC diagnostics record only method, fixed outcome, elapsed time and exception class; successful read polls are not logged, and repeated read failures are coalesced. These diagnostics never include signed media URLs, request bodies, headers or arbitrary provider error text. Cancellation still interrupts the resolver and reaps its process group before any later Open; there is no automatic replay of an uncertain Open.

## Prepared playback and cancellation

`ha_kodi_youtube_resolve.py` runs outside Kodi in a separately owned process group. It imports the unchanged, checksum-pinned SmartTube 0.5.3 metadata and DASH modules from their verified source buffers. The raw provider response must identify the requested video before parsing. The helper requires H264 video at 720/1080p plus non-DRC AAC and creates a private MPD. Each provider HTTP read has an eight-second timeout within the complete 45-second per-source preparation allowance. Timeout cleanup terminates and reaps the whole helper process group. The fireplace preparation path does not invoke yt-dlp or Deno. Kodi's tiny `plugin.video.hayoutube` adapter performs no extraction; it checks the current attempt generation immediately before resolving the already prepared stream.

InputStream Adaptive requires HTTP delivery of manifests. The existing host bridge serves only `GET /kodi/youtube/manifest?request_id=<attempt UUID>`, with its existing `X-HA-Host-Token` authentication. It verifies the current generation, fixed private path, size, and SHA256. There are no arbitrary filenames, upstream proxying, redirects, or new listeners. The host token appears only in ISA manifest headers; ordinary allowlisted YouTube headers appear only in media stream headers. The adapter rejects redirect/xlink manifests and media origins outside HTTPS Googlevideo.

The public voice request ID and private per-source attempt UUID have different purposes. Cancelling an attempt changes `~/.config/ha-host-actions/youtube/current-request.json`. The helper refuses late publication, the adapter refuses stale resolution, and the HTTP bridge refuses a stale MPD. The private descriptor and MPD live under `youtube/requests/<attempt UUID>/`; obsolete owned requests are bounded and cleaned without deleting the current generation, durable active/pending attempts, or unknown directories. Missing or unreadable selection history disables deletion, and protection is checked again immediately before removal.

Durable selection state is `~/.config/ha-host-actions/fireplace-selection.json`. It keeps the active, verified source separate from a pending preparing/prepared/opening candidate. The preparing record is durable before its generation becomes current. A crash before Open preserves the previous source and restores its manifest generation; a crash after Open requires fresh matching playback and progression before promotion when a valid repeat lease exists; an unleased pending candidate is fenced and stopped by exact identity. A definitively failed preparation also restores the previous generation. Explicit stop records durable cancellation and an intent sequence in the generation file; bridge close/restart does not invent a user stop. A newer start supersedes an older stop still waiting for the controller lock. Cancellation or an uncertain Open never revives an older attempt. If the same current uncertain attempt later has fresh, owned, exactly matching playback and progression, the monitor reconciles its generation, success receipt and history. It rechecks newer launch/stop intent and native identity after the durable write; explicit cancellation or foreign media prevents that reconciliation. Progress evidence must come from the same source, attempt and media identity, and final success publication rechecks stop intent after the durable history write. The existing `fireplace-owner.json` keeps prior repeat ownership for safe restoration. Selection state contains source IDs, timestamps, titles, and file hashes, not signed provider URLs. Provider URLs occur only in private, temporary playback files. Deleting selection history defeats the no-adjacent-repeat guarantee; repair an unreadable file explicitly rather than silently resetting it.

YouTube URLs may expire, disappear, or be restricted. A short live check proves startup and progression; it does not promise uninterrupted playback for the full advertised 10/12-hour upload. Each new command prepares fresh URLs, and source availability is evaluated afresh. A pair of quality-approved distinct local fallbacks is still pending; the stored unapproved clips do not satisfy that acceptance criterion. Do not redownload YouTube videos as an assumed freely licensed fallback.

## Validation and deployment

`.github/workflows/kodi-inputstream-portable.yml` builds the pinned upstream native addon on GitHub's ARM64 runner, runs upstream tests, and verifies every packaged ELF against the observed Odroid runtime and Kodi API ranges. Artifacts include the ZIP, relative checksum, licenses, provenance, target baseline, ELF verification, and automatic private logs. Install only a successful matching artifact; system package/loader overrides are unnecessary.

`.github/workflows/kodi-fireplace.yml` runs the host regression suite and executes the actual fireplace YAML through Home Assistant 2026.9.3. Its contract fixture downloads immutable, checksum-verified SmartTube 0.5.3 modules and exercises the real provider parser and DASH builder through the resolver, authenticated reader, and Kodi adapter. A separate contract retains coverage of the installed SendToKodi 0.10.3 builder and selector. `.github/workflows/ha-regressions.yml` runs the unchanged `make test-regressions` gate; the local shipping command verifies successful native receipts for the maintained, fireplace and Ruff workflows and every required job, rejecting a dirty worktree/index or a changed commit. All three workflows run on pushed branches and applicable pull requests; only exact-commit push receipts satisfy the shipping helper. Unit/HA tests and builds run only in genuine CI or managed Runpod. Local PCs and household devices are used for editing, read-only diagnostics, deployment, and bounded live playback checks.

Production has unrelated local commits and active HA changes. Deploy only these fireplace files, addon files, and new media assets after backing up their exact prior contents. Patch the existing bridge's fireplace/manifest handlers without replacing unrelated live functions. The integrated bridge imports `scripts/host/ha_host_fireplace.py`; any deployment of that bridge must install this sibling module in the same directory before restarting it. The module keeps the fireplace endpoints and bounded shutdown logic together while the bridge retains its outer authentication and audit boundary. A catalog or Evening-only deployment does not replace the running bridge or imply that this module has been installed. Reload the changed HA rest command, REST sensor, and script through supported services. Read projector/Kodi state before live checks; preserve human playback and restore only devices/volume changed by the check.
